# reservoir 改善・研究室LAN移設計画

作成日・更新日: 2026-10-10。backend/と追加されたfrontend/の静的調査に基づく暫定計画。アプリの実装と既存DBは変更していない。

## 目的と方針

2026-10-10追記: 認証は共通Basic認証＋予約別パスワード＋管理者認証で確定。共通Basic認証はON/OFF可能で、管理者認証と予約別パスワードは独立して維持する。インターネット・LANの両方に対応する。同一設備の重複禁止、設定可能なn日先制限、終了済み予約の変更禁止、Slack手動連絡を維持し、APIでも保証する。将来の設備別Slackチャネルへの自動通知を考慮する。具体的な再設計は../DESIGN.mdの確定要件を優先する。

研究室のメンバーが、設備や部屋の空き状況をすぐに確認し、少ない操作で予約・変更・取消できることを中心に置く。予約の正確さ、履歴の保全、担当者が引き継げる運用を改善する。Rust / Actix Web / SQLiteの現構成を出発点とし、Pi 4で実測して判断する。

## 調査で確認した構成

- main.rs: HTTP起動、API登録、全オリジンを許可するCORS設定。
- url_handler/: 利用者・リソース・予約のCRUD、FullCalendar用イベント取得。
- db_handler/: SQLxのSQLite接続プール（最大5接続）、テーブル初期化、SQL操作。
- model/: リクエスト、DB行、レスポンスの型、Unix秒とサーバーローカル日時の変換。
- utils.rs / reservoir.toml: カレントディレクトリ依存の設定、SHA-256による予約別パスワード。
- backend/README.md: API仕様。バックエンドの既存追跡ファイルは、移動後もGit HEADと同一内容であることを確認した。
- frontend/: React 18、MUI 5、FullCalendar 6、Day.js、Create React Appによる予約画面。
- frontend/src/Dashboard.js: 利用者・設備の取得とactiveによる選択肢の絞り込み、設備選択、カレンダーと登録フォームの状態管理。?machine=で設備を初期選択できる。
- frontend/src/Calendar.js: 週・月表示、期間選択、予約クリックによる編集、終了済み・利用中・24時間以内・将来の色分け。
- AddTargetEdit.js / ModTargetEdit.js / PasswordInput.js: 新規登録、予約詳細取得・変更・取消、予約別パスワード入力。
- API接続先はDashboard.jsのSakura VPS URLに固定。画面は/api/*へアクセスするが、バックエンドのルートは/users等である。既存プロキシでのパス変換が想定されるが、その設定は未確認。
- Basic認証、プロキシ、サービス起動設定はリポジトリ内にない。設備・利用者管理のリンク先は別ホストの/cgi-bin/machines.html、/cgi-bin/users.htmlであり、それらの実装も含まれていない。
- 同梱db/reservoir.dbは整合性検査がokだが、sqlite_sequence以外のテーブルがない。本番データとして扱わない。
- テスト、CI、DBマイグレーション、運用手順は見当たらない。
- cargo test --locked --offlineはactix-corsのローカルキャッシュ不足で実行できなかった。ビルド成功・失敗は未確認。

## 優先課題と実施順序

### 0. 現行運用と予約ルールを確定

Basic認証・プロキシ設定と別ホストの利用者・設備管理画面を確認し、画面→API→DBの経路を確定する。利用人数、対象設備、重複可否、capacityの意味、代理予約・編集権限、学外利用を確認する。本番DBのバックアップから、スキーマ、件数、不正日時、参照切れ、既存重複を調査する。既存利用手順とAPI互換性を記録する。

画面には「15日先まで予約」「終了済みは変更不可」「利用中は開始変更・取消不可」が実装されている。24時間以内の予約の短縮・開始延期・取消、利用中の終了繰上げではSlackへ連絡するよう案内がある。これらが正式な運用ルールか確認し、必要な制約はAPIでも保証する。Slackの自動送信処理はない。

完了条件: 画面を含む構成図、予約ルール、認証方針、本番データ移行対象が明確。

### 1. 予約とデータの正確さを修正（移設前の必須作業）

- 新規登録・更新で共通の検証処理を使う。更新は既存値と変更値を合成してstart < end、参照先の存在・有効状態を確認する。無効化後の既存予約をどう変更・取消できるかも定める。
- 重複禁止の設備では半開区間[start, end)を採用し、existing.start < new.end AND existing.end > new.startで検査する。更新時は自分の予約を除く。共有可能な設備はcapacityの意味を確定して別途設計する。
- 重複判定と保存を同一の書き込みトランザクションで行う。SQLiteのBEGIN IMMEDIATE相当の処理とbusy時の応答を検討し、同時予約テストで保証する。
- 予約・利用者・リソースの複数項目更新を単一UPDATEまたはトランザクションにし、途中までの保存を防ぐ。更新件数も確認する。
- 利用者・リソースはactiveによる無効化を通常操作とする。参照中の物理削除を拒否し、予約履歴を保つ。
- バージョン付きマイグレーションを導入し、参照整合性、日時制約、検索用インデックスを追加する。既存不正データを検出して修復方針を決めてから適用する。

完了条件: 不正な更新が保存されず、途中失敗でデータが変わらず、競合予約がルールどおり処理され、無効化で履歴が消えない。

### 2. API・認証・保守性を整備

- 作成用・更新用・取得用の型を分け、必須項目、空文字、文字数、capacityの範囲を検証する。省略とnullによる消去の意味を明確にする。
- エラーを400（入力不正）、404（不存在）、409（競合）、500（内部障害）等に整理する。内部DBエラーを利用者向け応答へ直接出さず、ログへ記録する。
- JSONエラーは文字列の手動連結をやめ、シリアライザーで生成する。既存画面の依存を確認してレスポンス変更を進める。
- FullCalendarの期間上限を排他的に扱う。予約一覧は並び順を固定し、期間指定・取得上限の方針を決める。
- 日時の保存・内部処理はUTC、表示は日本時間とし、サーバーOSのタイムゾーンへの依存を減らす。
- 設定を一度読み込み、設定ファイルの指定、絶対パス、初回DB作成を扱う。起動失敗は理由を明示する。
- LAN内での認証・編集権限を確定する。共通Basic認証、予約別パスワード、個人認証の役割を区別する。予約別パスワードを残す場合はソルト付きパスワードハッシュへの段階移行を設計する。
- 画面とAPIを同一オリジンで提供する構成を第一候補とし、必要なCORSだけ許可する。Basic認証を使う場合はHTTPSを含む通信経路を設計する。
- HTTPログ、ヘルスチェック、DB障害の記録を追加し、パスワードをログに残さない。
- Rustの整形、Clippy、API統合テストをCIで実行する。依存更新は互換性を確認して行い、未使用依存・コメントを整理する。

完了条件: 既存画面との互換性確認、主要APIテスト、障害の識別、認証・公開範囲の検証ができる。

### 3. 予約画面の改善（追加ソース確認済み）

画面の不具合修正を段階1・2と並行して優先する。

- AddTargetEdit.jsはHTTP成功判定をせず、JSONが読めればSuccessを表示する。共通APIクライアントを用意し、成功・入力不正・競合・認証失敗・通信障害を区別する。PasswordInput.jsも400/409/500やネットワーク障害を画面で表示する。
- 予約作成時のconsole.log(data)はパスワードも出力するため削除する。送信中のボタンを無効化して連打を防ぐ。
- PasswordInput.jsは末尾が:00+09:00でない日時にその文字列を付加するため、秒が00以外の日時や別オフセットを壊す。日時の解析・出力を統一し、開始と終了の前後関係も確認する。
- AddTargetEdit.jsの終了入力onErrorが開始エラーを更新している。開始・終了のエラーを分離し、空入力時のnull.add/null.formatによる例外も防ぐ。
- AddTargetEdit.jsとModTargetEdit.jsの利用者Autocompleteは、選択肢がvalueを持つのに比較でidを使っている。valueで比較し、選択解除とエラー解除も正しく扱う。
- 更新後のcalendarFlipは明示的なrefetchEventsを呼んでいない。表示期間・選択設備を保ちながら確実に再取得するようにし、ブラウザーで更新反映を検証する。
- 詳細取得中・失敗時に前の予約の値が残らないようにする。予約を素早く切り替えた際の応答順の逆転も防ぐ。パスワードダイアログを閉じる際は入力を消去する。
- Sakura VPS固定URLを相対/apiまたは環境設定へ変更する。Access-Control-Allow-Originをリクエストヘッダーへ付ける処理を除き、プロキシのパス変換とBasic認証範囲を画面・APIで統一する。
- 15日制限、終了済み・利用中の操作制限、Slack連絡ルールは正式な仕様を確認し、UIとAPIで揃える。色だけに頼らない状態表示にする。
- 固定幅300px、常設サイドバー、スマートフォンでのカレンダー表示を見直す。設備・日付・利用者の選択を簡潔にし、入力済みの値を競合エラーで失わないようにする。
- 未実装のReports/Laboratories/Saved reports、Recent Usage、テンプレート由来の文書・素材を整理する。設備・利用者管理の外部画面を統合するか、リンク先を構成設定にするか決める。
- 端末で前回選択した利用者・設備を記憶する場合は、代理予約の取り違えを防ぐ表示を入れる。無効な利用者・設備は新規予約から除外し、過去予約には表示する。
- フロントエンドの本番ビルド、入力境界、HTTP失敗時の表示、日時変換、更新反映を検証する。ビルド基盤・依存の更新は不具合修正と切り分ける。

完了条件: 研究室メンバーが説明なしで予約・変更・取消でき、他端末の変更も確認できる。

### 4. Raspberry Pi 4の運用を整備

OS・メモリ・保存先・電源を確認し、64bit Linux/ARM64でreleaseビルドを検証する。systemdサービス、専用実行ユーザー、自動起動・再起動、設定とDBの配置・権限を用意する。プロキシ経由ではAPIを127.0.0.1に置き、LANからの入口を限定する。IPまたは研究室内ホスト名、HTTPS、時刻同期を設定する。

DB接続数、busy timeout、WALの採否は実測して決める。電源断からの復旧、ログ容量、ディスク容量を確認する。バックアップはSQLiteの整合性を保つ方式で生成し、Pi以外にも保存する。保持期間、復旧担当、許容データ損失を決め、別環境への復元を実際に行う。

完了条件: 再起動後に利用でき、ピーク相当の同時操作を処理でき、バックアップから復元できる。

### 5. 移行リハーサルと本番切替

本番バックアップを使ってPiで移行・画面操作をリハーサルする。切替時はVPSへの書き込みを止め、最終バックアップ、転送、マイグレーション、整合性・件数確認を行う。閲覧・予約・変更・取消をLAN内端末で確認後、利用先を切り替える。旧サーバーは切戻し判断に必要な期間保持する。新サーバーで予約を受け付けた後に切戻す場合は、新しい予約の回収・反映手順を用意する。

完了条件: 最終データが一致し、LAN内で主要操作が成功し、二重運用を避けて切替・切戻しできる。

## 検証の重点

予約時間の境界、部分更新、存在しない参照先、無効状態、同時予約、更新途中の失敗、履歴保全、パスワード検証、旧DBからのマイグレーション、バックアップ復元を優先する。画面では秒が00以外の日時、入力消去、利用者選択、400/401/404/409/500と通信失敗、二重送信、予約切替、作成・変更・取消後の一覧反映を検証する。性能目標は利用人数・端末・同時操作数を確認後に決める。今回のフロントエンド再調査は静的確認であり、依存インストール・本番ビルド・ブラウザー操作は実施していない。
